---
name: kickoff-codex
description: Use when the user invokes $kickoff-codex or asks to use kickoff or asks to take a GitHub issue or a request from start to merge, with Opus workers, PickCheck, a QA pass, Astra and Fable reviews, and a gated merge.
---

Take the issue or request supplied with the skill invocation from intake to a merged PR and a closed issue. If it is empty, ask what to kick off. Invoking this skill to execute work is the user's standing opt-in for delegated workers, filing issues, and merging PRs that pass the gate below. Copying, editing, or reviewing this skill does not invoke that authorization. It never tags, releases, publishes packages, or dispatches workflows.

Intake. Resolve the target repo and read its `AGENTS.md`. For an issue, read the body and comments. For a request without an issue, search the repo's open and recently closed issues first (`gh issue list --state all --search ...`). If one matches, add the new details and an updated checklist to it and kick off that issue. Otherwise create an issue with a problem statement, acceptance criteria, and a checklist. In a public repo, leave out details of private projects. Work on a branch from a fresh `origin/main` in `~/Projects/.worktrees/<repo>/<branch>`. Never use `git stash`.

Plan and size. Scout inline until the work list and file ownership are clear, then record a short plan. Preserve Opus workers and Sol security-sensitive authoring. Read lanes_models, or the pickforge-lanes catalog when unavailable, for current model IDs and effort support. Check tools, credentials without exposing secrets, and execution mode before dispatch. A clear, contained change gets one worker at medium. Work with several parts or unclear interactions gets two or three workers at high, with disjoint files. Large work gets a read-only planning agent, then parallel workers at high. Use xhigh only for a reasoning gap shown at high. State the worker count and effort with a one-line reason. Security-sensitive authoring such as sandboxing, permissions, or credential handling goes to Sol. Worker briefs give owned files, required behavior, examples, validation commands, and scope limits. Tell workers they share the codebase and must preserve others' edits. Literally forbid `gh workflow run`, `gh release`, `npm publish`, `git tag`, and `sudo`. Workers own their tests.

Delegation. Use native Codex subagents for supported OpenAI models and Claude Code lanes for Anthropic workers. Use explicit model, effort, taskKind, and mode when dispatching lanes. Reviews are read-only; tests need shell access in a permitted workspace. In T3, discover provider and model IDs with orchestrator_capabilities. Use delegate_task for cross-provider or otherwise unsupported native dispatch when T3 orchestration is available. Retain task IDs and collect settled results before proceeding. T3 children inherit the calling thread's workspace. Bind the current thread to the task worktree through t3_worktree_handoff before delegating there. Do not create top-level threads as a substitute for child tasks. If required models or worktree binding are unavailable, report the specific blocker rather than silently substituting. Do not use Claude-only Workflow, agent(), SendMessage, or codex-run tools from Codex.

Verify. Run the repo's tests, lint, and type checks, then PickCheck as the pickcheck skill describes, on the final revision before publishing. Send violations back to the worker that owns the code.

QA pass. Run a device pass by default whenever there is something to drive: UI, CLI output, installers, or app behavior. Follow the device-pass skill. Use an isolated PickLab session for desktop apps and never drive the live desktop. Cover the happy path and the edge cases that matter for the change, such as empty, invalid, and boundary input, errors, cancellation, reload or restart persistence, and narrow viewports. Skip the pass only when there is nothing to drive, such as a pure internal refactor, docs, or CI config, and say why in the PR. A defect in the change is fixed in this PR and its journey rerun.

Open the PR. Push the branch and open a PR that uses `Closes #N`, after checking that N is the issue being finished. The body has a short summary, then a traceability matrix with one row per acceptance criterion or checklist item. The columns are requirement, how it was verified (automated test, device pass, or manual check), the scenario including edge cases, the result, and a link to the evidence. Keep evidence outside the repo. Register the PR with `link_pull_request` when available. Before finishing, check `list_thread_pull_requests` and link any missing PR from this work. Use `watch_pull_request` when waiting for checks in T3; resume verification when notified.

Review. Run two independent xhigh reviews of the exact diff, using Astra and Fable through the delegation routes above. A model never reviews its own code. If Astra authored code, Fable reviews it; if Fable authored code, Astra reviews it. Give reviewers the requirements, diff, revision, and validation evidence, but not the author's rationale or other reviewer's findings. Verify each finding through code or a focused test. Fix every valid finding, including small ones. Send fixes to the original worker session when the transport supports resuming it. Rerun affected checks and QA journeys, then recheck only the areas the fix touched. For T3, each review round uses a new delegate_task call with the original brief, prior findings, responses, and unresolved objections. Give each round a distinct clientRequestId, stable across retries. Do not continue reviews through t3_thread_send on a childThreadId. Allow up to three repair rounds. Stop earlier when the same findings recur or each fix creates new blocking findings. Bring unresolved findings to the user.

Follow-up work. Anything found during development, review, or QA that is outside this issue's scope becomes a new issue: a bug, enhancement, missing feature, flaky test, or debt the change did not cause. Search for a duplicate first and comment on it if one exists. Each issue says where it was found and links the PR. Do not fix it in this PR.

Merge gate. Merge only when every condition holds on the final head. CI is fully green; never merge while any check is failing or pending, including flaky ones. PickCheck passes. No review finding is unresolved. The diff stays within the issue's scope, and its checklist is complete. The QA pass succeeded or its skip is justified. The change does not touch database migrations, auth or permissions, deletion or migration of user data, release or signing config, feature-flag enabling, or exported APIs. Read the checks and decide first, then merge in a separate step with the repo's usual merge method. Retarget stacked child PRs to `main` before merging their base with `--delete-branch`. Confirm that the issue closed, update its checklist, and remove the worktree only when its cleanup is authorized and it has no uncommitted work.

When any gate condition fails, or the result needs a product decision, do not merge. Leave the PR open, send a push notification when that tool is available, and tell the user what needs their decision and why, with the PR link.

Finish with a visual report, so the user can understand each PR without opening it. For several PRs, give one short card per PR: a QA screenshot, the issue it closes, what the user sees, why it needs the user, and any open point or decision taken. Add more screenshots or a short screen recording when one image does not show the change. For one PR, give more detail: the main journeys with their screenshots, the edge cases covered, the risks, and the open points. Show the report with `html_render` when that tool is available; otherwise embed the images in Markdown with absolute paths. Use only real evidence, and say when a PR has no screen to show. Then give the merge order, the issue states, the follow-up issues filed, the QA evidence links, and what waits on the user, with the answers the user can give.

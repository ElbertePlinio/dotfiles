---
name: kickoff
description: Use when the user runs /kickoff or says "kickoff", or asks to take a GitHub issue or a request from start to merge.
---

Take the issue or request in $ARGUMENTS to a merged PR and a closed issue. If it is empty, ask what to kick off with the question tool. Kickoff is full-send plus issue tracking, a QA pass, and a visual report. It is the user's standing opt-in for the Workflow tool, for filing issues, and for merging PRs that pass the gate. It never tags, releases, publishes packages, or dispatches workflows. If the request also says "full stop", follow the full-stop skill at the end instead of merging.

Intake. Resolve the target repo and read its `AGENTS.md`. For an issue, read the body and comments. For a request without an issue, search open and recently closed issues first with `gh issue list --state all --search ...`. If one matches, add the new details and an updated checklist to it. Otherwise create an issue with a problem statement, acceptance criteria, and a checklist. In a public repo, leave out details of private projects. Work on a branch from a fresh `origin/main` in `~/Projects/.worktrees/<repo>/<branch>`. Never use `git stash`.

Plan and size. Scout inline until the work list is clear. Do the work yourself by default; workers cost a briefing and a context each. Delegate only parts that are independent and large: a Workflow with Opus workers at medium and disjoint files, high only for unclear interactions, xhigh only for a gap shown at high. Large work gets a planning agent first, then workers with `isolation: 'worktree'`. Security-sensitive authoring, such as sandboxing, permissions, or credential handling, goes to Sol: `delegate_task` in T3, or `codex-run author` elsewhere. State the worker count and effort with a one-line reason. Briefs give owned files, required behavior, examples, validation commands, and scope limits, and forbid `gh workflow run`, `gh release`, `npm publish`, `git tag`, and `sudo`. Workers run focused tests. The lead runs full suites and end-to-end runs.

Then follow the full-send skill from its proof step, with these additions.

QA pass. Proof includes a device pass whenever there is something to drive: UI, CLI output, installers, or app behavior. Follow the device-pass skill, and use an isolated PickLab session for desktop apps, never the live desktop. Cover the happy path and the edge cases that matter: empty, invalid, and boundary input, errors, cancellation, reload or restart persistence, and narrow viewports. Skip it only when nothing can be driven, such as a pure refactor, docs, or CI config, and say why in the PR. Fix a defect in this PR and rerun its journey. Run the QA pass while a Sol round runs.

Review. Use sol-loop. Add a Fable review with `final-reviewer-high` when the change turns on frontend, visual judgment, architecture intent, or ambiguous product behavior, with Opus at the same effort when Fable is unavailable. Use the council skill instead when the change carries security, auth, permissions, money, migration, persistence, concurrency, or data-loss risk. No model reviews code it wrote. Give reviewers the requirements, diff, revision, and validation evidence, not the author's rationale or another reviewer's findings. Send fixes to the original worker only if it has been idle under 5 minutes; otherwise fix small items yourself or brief a fresh worker.

PR. Use file-pr with `Closes #N`, after you check that N is the issue you finish. Add a traceability matrix with one row per acceptance criterion or checklist item: requirement, how it was verified, scenario with edge cases, result, and an evidence link. Keep evidence outside the repo.

Follow-ups. Anything found outside this issue's scope becomes a new issue: a bug, missing feature, flaky test, or debt the change did not cause. Search for a duplicate first and comment on it if one exists. Say where you found it and link the PR. Do not fix it in this PR.

Merge gate. Use full-send's gate, plus these conditions: the issue checklist is complete, and the QA pass succeeded or its skip is justified. Migrations, auth, Stripe, data changes, feature flags, and exported APIs need the proof full-send describes and a written rollback path, not the user. Stop only for the hard stops in your global instructions. Merge in a separate step with the repo's usual method. Retarget stacked child PRs to `main` before you merge their base with `--delete-branch`. Confirm the issue closed, update its checklist, and remove the worktree.

Report. Show a visual report with `html_render` when the change has a screen, built only from real QA screenshots: what the user sees, the issue it closes, the edge cases covered, and any risk. Otherwise give a short text report. Then give the merge order, the issue states, the follow-up issues, and the evidence links. Anything that waits on the user goes through the question tool, with options and your recommendation first.

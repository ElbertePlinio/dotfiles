---
name: kickoff
description: Use when the user runs /kickoff or asks to take a GitHub issue or a request from start to merge, with Opus workers, PickCheck, a QA pass, Astra and Fable reviews, and a gated merge.
---

Take the issue or request in $ARGUMENTS from intake to a merged PR and a closed issue. If it is empty, ask what to kick off. This skill is the user's standing opt-in for the Workflow tool, for filing issues, and for merging PRs that pass the merge gate below. It never tags, releases, publishes packages, or dispatches workflows.

Intake. Resolve the target repo and read its `AGENTS.md`. For an issue, read the body and comments. For a request without an issue, search the repo's open and recently closed issues first (`gh issue list --state all --search ...`). If one matches, add the new details and an updated checklist to it and kick off that issue. Otherwise create an issue with a problem statement, acceptance criteria, and a checklist. In a public repo, leave out details of private projects. Work on a branch from a fresh `origin/main` in `~/Projects/.worktrees/<repo>/<branch>`. Never use `git stash`.

Plan and size. Scout inline until the work list and file ownership are clear, then load the workflow-authoring skill and run the implementation as a Workflow. Every `agent()` call sets `model: 'opus'` and an explicit effort, so no leaf inherits the session model. Size by ambiguity and risk, not diff size. A clear, contained change gets one worker at medium. Work with several parts or unclear interactions gets two or three workers at high, with disjoint files. Large work gets a planning agent, then parallel workers with `isolation: 'worktree'`, at high, with xhigh only for a reasoning gap shown at high. Before launching, state the worker count and effort with a one-line reason. Security-sensitive authoring such as sandboxing, permissions, or credential handling goes to Sol through the codex skill (`codex-run author`) instead of Opus. Worker briefs give owned files, required behavior, examples, validation commands, and scope limits, and literally forbid `gh workflow run`, `gh release`, `npm publish`, `git tag`, and `sudo`. Workers own their tests.

Verify. Run the repo's tests, lint, and type checks, then PickCheck as the pickcheck skill describes, on the final revision before publishing. Send violations back to the worker that owns the code.

QA pass. Run a device pass by default whenever there is something to drive: UI, CLI output, installers, or app behavior. Follow the device-pass skill. Use an isolated PickLab session for desktop apps and never drive the live desktop. Cover the happy path and the edge cases that matter for the change, such as empty, invalid, and boundary input, errors, cancellation, reload or restart persistence, and narrow viewports. Skip the pass only when there is nothing to drive, such as a pure internal refactor, docs, or CI config, and say why in the PR. A defect in the change is fixed in this PR and its journey rerun.

Open the PR. Push the branch and open a PR that uses `Closes #N`, after checking that N is the issue being finished. The body has a short summary, then a traceability matrix with one row per acceptance criterion or checklist item. The columns are requirement, how it was verified (automated test, device pass, or manual check), the scenario including edge cases, the result, and a link to the evidence. Keep evidence outside the repo. Register the PR with `link_pull_request` when the t3-code MCP is available.

Review. Run two independent xhigh reviews of the exact diff. Astra runs through the codex skill (`codex-run review --rev <head> --effort xhigh`). Fable runs as the native `final-reviewer-xhigh` agent. Give each reviewer the requirements, the diff, the revision, and the validation evidence, but not the author's rationale or the other reviewer's findings. Verify each finding through code or a focused test. Fix every valid finding, including small ones. Send the fixes to the original worker, with `SendMessage` for Opus or `codex-run author --resume` for Sol, rerun the affected checks and QA journeys, and have the reviewer who raised a finding recheck only the areas the fix touched, resuming the Astra session with `--resume` at the new head. Allow up to three repair rounds. Stop earlier when rounds stop converging: the same findings recur, or each fix creates new blocking findings. What is still unresolved then goes to the user.

Follow-up work. Anything found during development, review, or QA that is outside this issue's scope becomes a new issue: a bug, enhancement, missing feature, flaky test, or debt the change did not cause. Search for a duplicate first and comment on it if one exists. Each issue says where it was found and links the PR. Do not fix it in this PR.

Merge gate. Merge only when every condition holds on the final head. CI is fully green; never merge while any check is failing or pending, including flaky ones. PickCheck passes. No review finding is unresolved. The diff stays within the issue's scope, and its checklist is complete. The QA pass succeeded or its skip is justified. The change does not touch database migrations, auth or permissions, deletion or migration of user data, release or signing config, feature-flag enabling, or exported APIs. Read the checks and decide first, then merge in a separate step with the repo's usual merge method. Retarget stacked child PRs to `main` before merging their base with `--delete-branch`. Confirm that the issue closed, update its checklist, and remove the worktree.

When any gate condition fails, or the result needs a product decision, do not merge. Leave the PR open, send a push notification when that tool is available, and tell the user what needs their decision and why, with the PR link.

Finish with the PR, the issue state, the follow-up issues filed, the QA evidence link, and anything waiting on the user.
